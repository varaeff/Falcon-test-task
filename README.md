# Учёт рабочего времени

Тестовое приложение Vue 3 для учёта времени с общей базой Supabase.

Документация: [архитектура фронтенда](Docs/frontend-architecture.md) и [описание базы данных](Docs/database.md).

## Использованный стек и инструменты

- **Клиент:** Vue 3, TypeScript, Tailwind CSS и Vite.
- **Сервер и данные:** Supabase, PostgreSQL и серверные функции базы данных.
- **Проверки и форматирование:** Node.js Test Runner, `vue-tsc` и Prettier.
- **Разработка с ИИ:** OpenAI Codex с моделью GPT-6.1 Terra, уровень размышлений Medium. Скил GrillMe использовался для уточнения требований, OpenSpec — для подготовки и ведения спецификаций, проектных решений и задач.

## Примеры запросов к ИИ

При работе над проектом я, в частности, обращался к Codex с такими запросами:

> Проведи полный анализ кода.
> Можно ли что-то упростить? Оптимизировать? Есть ли дублирование кода?
>
> Пока ничего не меняй, дай отчет и предложения, если они будут

> Реализуй исправления по пунктам 1 (параллельные обновления и устаревшие данные), 2 (смешение действия и обновления данных), по пункту 3 приведи к единому варианту хранения - с точностью до секунды. 4 - загружать только отчет за выбранный период и отдельно данные для проверки интервалов.

> В панели статистики при изменении интервала задачи должны выполняться следующие правила:
>
> - после корректного сохранения данных кнопки сохранить и отмена должны скрываться, внешний вид - как до редактирования (вариант с кнопками изменить и удалить)
> - временной итервал при изменении не должен уходить в будущее и пересекаться с другими интервалами этого сотрудника. Если условие не соблюдается, некорректная граница должна выделяться красным, кнопка сохранения не должна быть доступна

## Найденные ошибки и улучшения

- Изначально ИИ сгенерировал один composable. Я разделил работу с сессией, загрузку данных и расчёт отчёта между отдельными composables. Действия с API вынес из корневого компонента, чтобы компоненты занимались преимущественно отображением.
- Исправил загрузку статистики: вместо всей истории запрашиваю записи за выбранный период, а данные для проверки пересечений загружаю отдельно при редактировании. Активный таймер получаю отдельным запросом.
- Защитил интерфейс от устаревших ответов: результат предыдущего запроса не перезаписывает данные после смены периода, сессии или начала нового обновления. Также разделил результат сохранения и последующего обновления, чтобы не предлагать повторять уже выполненное действие.
- Исправил редактирование интервалов: после успешного сохранения форма закрывается, некорректные границы подсвечиваются, а сохранение блокируется. На сервере сохраняются проверки пересечений и времени; хранение приведено к точности до секунды.
- Добавил состояния загрузки и повторную загрузку при ошибке, а также тесты расчётов, асинхронных обновлений, повторного запуска таймера и пустого отчёта.

## Настройка

1. Создайте проект Supabase и дождитесь его запуска.
2. Выполните миграции из `supabase/migrations` по порядку в SQL Editor проекта. Первая миграция создаёт сотрудника «Администратор» с ролью администратора. При необходимости измените имя в первой миграции до её применения. Миграция точности времени остановится, если существующий интервал после округления вниз станет короче секунды: такие записи необходимо исправить перед повторным запуском.
3. Скопируйте `.env.example` в `.env.local`, укажите `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY` из настроек проекта. Не используйте service role key в клиенте. Пароли и другие секреты не должны иметь префикс `VITE_`: Vite предоставляет такие переменные клиентскому коду.
4. Выполните `npm ci`, затем `npm run dev`. Проверки: `npm test` и `npm run build`.

Для Vercel импортируйте репозиторий, задайте те же публичные переменные окружения и запустите развёртывание. `vercel.json` задаёт сборку и каталог результата. Убедитесь, что Supabase доступен: бесплатный проект может быть приостановлен и потребовать восстановления в панели Supabase. Для отката приложения выберите предыдущую сборку Vercel; данные базы автоматически не удаляются.

## Ограничения безопасности

Вход по имени не подтверждает личность. Любой, кто имеет доступ к приложению и публичному API, может войти как любой сотрудник, в том числе администратор. Проверки сессии и роли защищают обычный сценарий работы, но не заменяют аутентификацию и защиту от поддельных запросов. Решение предназначено только для демонстрации в доверенной среде, не для реальных чувствительных данных. Для эксплуатации необходимы полноценная аутентификация и правила доступа.

Отчёт использует часовой пояс устройства; результаты за одинаковые календарные даты в разных поясах могут отличаться. Таймер продолжает идти при закрытии страницы и отсутствии сети, но для сохранения действий требуется соединение.
