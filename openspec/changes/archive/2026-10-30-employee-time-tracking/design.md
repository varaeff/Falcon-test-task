## Context

Проект создаётся с нуля; требования и доверительная модель описаны в proposal и specs. Клиенты на разных устройствах используют общую базу, без собственного приложения-сервера и без подтверждения личности.

## Goals / Non-Goals

**Goals:** Сохранение данных между устройствами, согласованность таймеров и сессий при конкурентных запросах, простая настройка.

**Non-Goals:** Безопасная идентификация, защита от злонамеренного клиента, офлайн-синхронизация и производство с реальными чувствительными данными.

## Decisions

- Vue 3, TypeScript без типа `any`, Vite и Supabase PostgreSQL. Локальное хранилище само по себе не обеспечивает общие данные. Supabase предоставляет общую базу и API без отдельного приложения-сервера.
- Таблица сотрудников содержит идентификатор, нормализуемое имя, признак администратора и текущий идентификатор сессии; записи содержат идентификатор сотрудника, описание, начало и nullable окончание в timestamptz. SQL-миграция создаёт начального администратора; клиент получает только публичный ключ, секретный ключ в браузер не включается.
- При каждом явном входе генерируется новый случайный идентификатор сессии и атомарно заменяет прежний. Идентификатор хранится в sessionStorage вкладки, восстанавливается при обновлении и проверяется при запросах и периодически или через подписку; при несовпадении происходит выход. На каждой мутации база проверяет актуальность сессии и роль, однако без подтверждения личности это только защита обычного сценария, а не от подделки запросов. Выход условно очищает только свою текущую сессию, не затрагивая новую.
- Критичные операции выполняются атомарно в функциях PostgreSQL: проверка сессии и роли, назначение роли с защитой последнего администратора, запуск и остановка, изменение и удаление записи. Ограничения и транзакционная блокировка для сотрудника предотвращают пересекающиеся интервалы и несколько активных таймеров при гонках. Интервалы полуоткрытые [начало, конец), соседние допустимы; активный интервал открыт в будущее. Серверное время определяет начало и остановку и проверку будущего окончания.
- Отчёт использует локальные календарные границы устройства: начало первого дня включительно и начало дня после последнего исключительно, с учётом переходов часового пояса. Каждая запись обрезается по границам и текущему времени для активного таймера; список показывает исходные интервалы. Неделя начинается в понедельник. Интерфейс обновляет длительность активных записей на открытой странице.
- Доступ к общей базе в тестовом режиме открывается только необходимыми публичными операциями; прямой доступ к таблицам ограничивается, где возможно. Даже вызовы функций с проверкой сессии не обеспечивают полноценной защиты без аутентификации: любой может войти как администратор. Не использовать сервисный ключ и не заявлять это решением для настоящей компании.

## Risks / Trade-offs

- [Подмена сотрудника и администратора] → Явно документировать тестовую доверительную модель; для реальной эксплуатации требуется подтверждение личности и правила доступа.
- [Приостановка бесплатного проекта или лимиты] → Документировать восстановление проекта и необходимость доступного Supabase перед демонстрацией.
- [Различные часовые пояса и часы устройств] → Для сохранения использовать серверное время, в отчёте явно показывать локальный часовой пояс; итоги по одним датам на разных устройствах могут различаться.
- [Потеря сети или конкурирующие действия] → Показывать ошибки, повторно загружать состояние после конфликтов, не подтверждать несохранённые операции.

## Migration Plan

Создать проект Supabase, применить схему и начальные данные, настроить публичные параметры окружения клиента и собрать приложение. Инструкции должны позволять повторить настройку и проверить приложение.
